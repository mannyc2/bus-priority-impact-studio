# Web App Support Plan

## Purpose

The web app is now route-first and projection-backed, but it still needs a stronger product support
plan for three connected surfaces:

1. **Briefs** as the polished public output.
2. **Composer workflows** for drafting, evidence attachment, review, and history.
3. **Data loading performance** so route transitions, brief reading, and composer work do not
   waterfall or over-fetch.

This page extends [[web_api_endpoint_architecture|Web API Endpoint Architecture]],
[[website_hard_cutover_plan|Website Hard Cutover Plan]], and
[[web_observability_performance_seo_plan|Web Observability, Performance, and SEO Plan]].

## Current State

Current app facts:

- TanStack Router is already configured with `defaultPreload: "intent"` and
  `defaultStructuralSharing: true`.
- Production Studio pages call `/api/v1/studio/*` loaders and no longer use sample-data fallback
  branches.
- Studio endpoint projections are generated by `bun run build:studio-release` and served from
  private `studio/v1/*` R2 keys through RESTful Worker URLs.
- Route modules currently use simple loaders such as `fetchStudioBrief`, `fetchStudioRoute`, and
  `fetchStudioCompare`.
- Search, compare, and new-brief routes already use `loaderDeps` for the search params they
  consume.
- The brief composer is currently a projection-seeded UI with local component state for selected
  claims/evidence. It is not yet a persisted draft system.

## Principles

- Route loaders own page data orchestration. Page components should not begin critical network
  fetches after render.
- Start independent requests early and run them in parallel.
- Use TanStack Router cache for read-mostly release projections before adding another cache.
- Introduce TanStack Query only if composer mutations need shared optimistic updates,
  route-spanning invalidation, or persisted mutation state.
- Keep D1 compact. Mutable draft rows can live in D1 only if they are bounded and product-facing;
  large body snapshots, exports, and evidence bundles belong in R2.
- Never compute heavy analytics in a public request handler. If the composer needs a metric, expose
  it through a release projection or mark the section unavailable.
- Missing data should be a typed unavailable state, not a fixture fallback.

## Data Loading Strategy

### Router Cache First

Use TanStack Router's built-in stale-while-revalidate cache for the read-heavy Studio app.

Suggested route cache policy:

| Route class | Examples | Loader behavior | Freshness |
|---|---|---|---|
| Release metadata | `/`, `/methods`, `/docs` | Await one compact projection | `staleTime: 10 min`, background reload |
| Lists/cards | `/briefs`, `/findings`, `/search` | Await compact list projection; use `loaderDeps` for query only | `staleTime: 2-5 min` |
| Route detail | `/routes/$routeId` | Await critical route projection; defer map/evidence refs later | `staleTime: 5-10 min` |
| Ladder/map-heavy | `/routes/$routeId/ladder` | Await ladder index; defer heavy geometry/artifact reads | `staleTime: 5 min` |
| Published brief | `/briefs/$briefId` | Await narrative shell; defer evidence graph/history | `staleTime: 10 min` |
| Composer draft | `/briefs/new`, `/briefs/$briefId/edit` | Await draft shell; prefetch evidence/caveats/route context in parallel | `staleTime: 0-30 sec`, `gcTime` short |
| Review/history | `/briefs/$briefId/review`, `/briefs/$briefId/history` | Await comments/version list; defer diffs/body snapshots | `staleTime: 30-60 sec` |

Avoid `staleTime: Infinity` for production Studio routes until the app has a release-id invalidation
hook. The data is monthly/static, but users can keep a tab open across deploys or release
promotions.

### Loader Shape

Update API client helpers to accept an optional `AbortSignal`:

```ts
fetchStudioBrief(briefId, { signal: abortController.signal })
```

Each loader should pass the router `abortController.signal` so abandoned navigations cancel
in-flight fetches.

Use object-form loaders when configuring cache behavior:

```ts
loader: {
  handler: ({ params, abortController }) =>
    fetchStudioBrief(params.briefId, { signal: abortController.signal }),
  staleReloadMode: "background",
},
staleTime: 10 * 60 * 1000,
```

Use `loaderDeps` narrowly. Include only search params that the loader uses. For example, `/compare`
should depend on `a` and `b`, while UI-only view state should stay out of loader deps.

### Deferred Data

Use deferred loader values for slow, non-critical data:

- Brief reading should render the title, summary, claims, KPIs, and body first. Evidence graph,
  raw citation payloads, export metadata, and version history can resolve behind `<Await>`.
- Route detail should render route identity, KPIs, diagnosis, and top slow segments first. Map
  manifest reads and detailed segment geometry can resolve after the shell.
- Composer should render draft outline and active claim first. Evidence inspector payload,
  caveat library, related route metrics, and review context can load in parallel and suspend only
  their panel.

Do not defer data that determines route existence, permissions, or the canonical title/meta.

### Prefetching

Keep `defaultPreload: "intent"` and add explicit prefetch conventions:

- Route/brief/finding cards should use `Link` with intent preloading.
- On brief cards, preload the published brief projection only; evidence/history should load when
  that tab is opened.
- On route detail, preload ladder only when the ladder link receives intent.
- Composer action buttons can prefetch the draft shell, not the entire evidence library.

## Briefs Plan

Briefs should become the highest-confidence public output, not just another route page.

### Brief Read Models

Keep published brief contracts split by use:

| Contract | Purpose |
|---|---|
| `StudioBriefsResponse` | Gallery cards and filters |
| `StudioBriefResponse` | Published brief body, claims, KPIs, caveats |
| `StudioBriefEvidenceResponse` | Evidence graph, raw citations, source snippets, metric provenance |
| `StudioBriefHistoryResponse` | Version list, release month, body/artifact hashes |
| `StudioBriefExportManifest` | PDF/Markdown/HTML export refs and checksums |

The current implementation reuses `StudioBriefResponse` for evidence/history endpoints. Split these
contracts before adding real evidence/history pages so brief reading does not pull unnecessary
payloads.

### Brief Product Requirements

Every published brief should expose:

- release month and provenance labels,
- route/corridor identity,
- headline finding and claim list,
- citation count and evidence quality,
- caveats and unavailable sections,
- artifact hashes and generated timestamps,
- methodology gate status, especially for intervention claims,
- export links only when the corresponding R2 artifact exists.

March 2026 observed reliability must be labeled `third_party_recovered`; official self-collected
May evidence must be labeled separately until May speed rows are published.

## Composer Plan

The composer should move in phases so the UI can mature without inventing an unsafe collaboration
backend too early.

Composer generation must follow [[wiki/project/ai_interaction_model|AI Interaction Model]]: AI
drafts typed claims, evidence links, caveats, reviewer notes, and publish candidates, not free-form
chat replies.

### Phase 0: Projection-Seeded Local Composer

Current state. Keep it useful for design validation:

- `/briefs/new?route=` and `/briefs/new?finding=` seed from existing release projections.
- `/briefs/$briefId/edit` loads the published/draft-shaped brief projection.
- Claim selection, evidence toggles, and caveat toggles are local component state.
- No publish action writes to production data.

Add route-loader improvements here first: parallel seed fetches, abort signals, short cache times,
and panel-level deferred evidence.

### Phase 1: Single-User Draft API

Add a feature-flagged draft surface when the read-side is stable:

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/studio/briefs` | Create draft from route/finding/segment context |
| `GET /api/v1/studio/briefs/:briefId/draft` | Read draft editor payload |
| `PATCH /api/v1/studio/briefs/:briefId` | Update title/dek/body outline |
| `POST /api/v1/studio/briefs/:briefId/claims` | Add claim |
| `PATCH /api/v1/studio/briefs/:briefId/claims/:claimId` | Edit claim text, evidence refs, caveats |
| `POST /api/v1/studio/briefs/:briefId/generate` | Deterministic draft refresh from selected evidence |
| `POST /api/v1/studio/briefs/:briefId/reviews` | Add review comment/request changes |
| `POST /api/v1/studio/briefs/:briefId/publish` | Create a publish candidate artifact, not direct production promotion |

Draft rows may live in D1 if bounded:

- Store draft metadata, claim text, review comments, and references to immutable release artifacts.
- Store large generated bodies, diffs, and export candidates in R2.
- Do not store raw analytics history or source snapshots in draft tables.
- Add a draft lifecycle: `draft`, `in_review`, `approved`, `publish_candidate`, `published`,
  `archived`.

### Phase 2: Review And Version History

Add review/history contracts:

- `BriefReviewThread`
- `BriefReviewComment`
- `BriefVersion`
- `BriefDiffSummary`
- `BriefPublishCandidate`

Review comments should attach to stable anchors: claim id, section id, evidence id, or body range.
Version history should compare artifact hashes and structured claims before rendering text diffs.

### Phase 3: Publishing

Publishing should be deliberate:

1. Validate claim evidence and caveats.
2. Validate methodology gates and block unsupported causal wording.
3. Render JSON/Markdown/HTML/PDF candidates.
4. Write candidate artifacts to R2 with hashes.
5. Require an explicit promotion command or admin-only action to update the public projection set.

Do not let a normal page request mutate the public March release.

## API And Projection Work

Immediate contract work:

1. Split brief evidence/history response schemas from `StudioBriefResponse`.
2. Add `StudioDraftBrief*` schemas for composer payloads behind a feature flag.
3. Add a release/projection manifest that includes `releaseId`, `baselineMonth`, generated time,
   route count, brief count, and schema version.
4. Add ETag or content-hash headers to Studio projection responses so browser and Worker caches can
   avoid redundant payload transfer.
5. Return section-level `quality` for unavailable evidence instead of 404ing the whole page when a
   non-critical panel is missing.

Worker rules:

- Read endpoints may serve private R2 projection keys.
- Write endpoints must validate Zod bodies, enforce feature flags/auth decisions, and avoid
  request-time analytics.
- All Studio handlers should emit `Server-Timing` and structured route-template logs.

## Implementation Checklist

1. Add signal-aware Studio API client helpers.
2. Convert high-traffic route loaders to object-form loaders with route-specific `staleTime`.
3. Split `/briefs/$briefId/evidence` and `/history` schemas/projections from the full brief body.
4. Add deferred panel loading for brief evidence/history and route map-heavy payloads.
5. Add composer draft schemas and local feature-flagged endpoints, but keep publish disabled.
6. Add Worker tests for projection missing/invalid states and draft feature-flag behavior.
7. Add web performance checks that fail on route-loader waterfalls where a page serially fetches
   independent projections.
8. Update `/docs` and generated OpenAPI after each public contract change.

## Verification

Minimum checks for these changes:

```bash
bun run check:types
bun run check:web-architecture
bun run test:web
bun run test:worker
bun run check:web-release
```

For data-loading changes, add route-level tests or smoke checks that prove:

- search/compare loader deps only include used params,
- aborted navigations cancel fetches,
- evidence/history panels do not block brief shell rendering,
- draft mutations do not invalidate unrelated route projections,
- missing non-critical projections render typed unavailable states.

## Source Note

This plan follows the TanStack Router data-loading guidance supplied in the 2026-05-18 project
handoff: route loaders should coordinate async work early, use loader deps for cache keys, lean on
SWR route cache for read-heavy pages, use abort signals, and defer slow non-critical data behind
Suspense/Await.
