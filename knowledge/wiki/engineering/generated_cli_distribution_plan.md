# Generated CLI And Distribution Plan

## Purpose

The public CLI should be generated from the same product contract as the Worker API and docs, then
shipped as compiled binaries through package-manager wrappers.

The pipeline is one system:

```text
runtime TypeScript schema
  -> generated IR
  -> OpenAPI, docs, SDK/MCP metadata, CLI command tree
  -> apps/cli/src/index.ts
  -> bun build --compile
  -> signed/notarized binaries
  -> CliReleaseManifest
  -> npm, PyPI, Homebrew, and later Windows wrappers
```

The binary is the handoff. The schema/generation layer decides what commands exist. The distribution
layer ships the compiled result. Package managers are delivery mechanisms; they are not the product
contract.

## Source Of Truth

OpenAPI is an output, not the input.

The source of truth must be a runtime TypeScript schema value, not erased TypeScript types. Use a
builder or Zod-backed value that generators can read at runtime, with TypeScript types inferred from
that value. This mirrors the release-manifest rule: one runtime contract, many renderers.

The schema must model more than REST:

- REST operations and their request/response contracts.
- CLI command names, args, flags, prompts, local filesystem effects, and output contracts.
- Locality: `remote`, `local-mirror`, or `both`, plus the default.
- Workers binding/RPC surfaces when a product can be invoked from runtime bindings.
- Agent-facing context: docs snippets, examples, caveats, changelog entries, and skill metadata.
- Output shape for every command's `--json` result.

The generated intermediate representation should be product-scoped so changes remain reviewable at
100+ products and thousands of operations.

## Schema Rules

The schema layer enforces a closed vocabulary:

- Verb names are enums, not free text.
- Use `get`, never `info`.
- Always support `--json`; use it as the stable agent contract.
- Use `--force`, never `--skip-confirmations`.
- Avoid parallel names across surfaces. If the CLI says `get`, docs, SDK examples, and generated MCP
  descriptions should use the same concept.

Locality is first-class:

- Each operation declares where it can run: remote, local mirror, or both.
- `--local` and remote execution must use shape-identical operation contracts where both are
  supported.
- When a local mirror exists, generate its OpenAPI surface from the same schema as the remote API.
- Add a conformance test that compares the remote and local operation sets and fails on drift.

Overrides are allowed only inside guard rails:

- Product teams may tune command names, descriptions, examples, and grouping.
- Overrides may choose from the allowed verb/flag vocabulary only.
- A schema linter rejects disallowed verbs, flags, aliases, missing `--json`, missing output schemas,
  and local/remote shape drift.
- A drift check rejects generated CLI/docs/OpenAPI changes that did not originate from a schema
  change.

## Generated Outputs

Generators fan out from one IR:

| Output | Owner | Rule |
|---|---|---|
| CLI command tree and dispatcher | `apps/cli` | Generated by default, hand-written adapters only at the edge |
| OpenAPI | `packages/domain` / `apps/web` | Output from schema, not hand-written |
| Worker API handlers | `apps/web/src/worker` | Thin handlers over serving projections |
| Docs | `apps/web/src/studio/pages/docs.tsx` and generated markdown | Left-sidebar, Vercel-style explanatory tone, agent-readable raw markdown |
| SDK/MCP metadata | future packages | Generated from OpenAPI or the shared IR |
| Agent Skills | future artifacts | Generated with examples, safety notes, and command contracts |
| Wrangler/config schema equivalents | future artifacts | Generated JSON Schema where config exists |

Do not make public request handlers import pipeline-only code. If the generated surface needs data
that is not in D1/R2, add a serving projection or return a designed unavailable state.

## Distribution Contract

`CliReleaseManifest` is the only contract between compiled binaries and package-manager wrappers.

It should live in a shared package that can be imported by release scripts, tests, and docs
generators. The likely home is a future `packages/core` or `packages/cli-contracts`; if we keep this
repo's current package model, `packages/domain` can host the first schema until a dedicated package
exists.

Required manifest fields:

```ts
type CliReleaseManifest = {
  manifestVersion: 1;
  packageName: "bpi";
  version: string;
  schemaVersion: string;
  schemaCommit: string;
  generatedSourceCommit: string;
  builtAt: string;
  artifacts: Array<{
    platform: "darwin" | "linux" | "win32";
    arch: "arm64" | "x64";
    libc?: "glibc" | "musl";
    url: string;
    sha256: string;
    size: number;
    signed: boolean;
    notarized?: boolean;
  }>;
};
```

Every renderer is a pure function:

```text
CliReleaseManifest -> staged package
```

If a package wrapper needs information not present in the manifest, the manifest is incomplete.

## Release Order

The release pipeline order matters:

1. Resolve schema commit and validate generated output is clean.
2. Generate CLI source and docs/API artifacts.
3. Build one binary per target with `bun build --compile`.
4. Sign macOS binaries.
5. Notarize macOS binaries.
6. Compute `sha256` and byte length from the final signed bytes.
7. Write and validate `CliReleaseManifest`.
8. Render package-manager wrappers from the manifest.
9. Audit final package archives, wheels, and formulae.
10. Publish wrappers and upload manifest/provenance.

Never hash macOS binaries before signing/notarization. Signing mutates bytes.

## Package-Manager Wrappers

### npm

Use the esbuild/swc-style umbrella package:

- Publish `@bp/cli` as the umbrella package.
- Publish platform packages such as `@bp/cli-darwin-arm64`, `@bp/cli-linux-x64`, and so on.
- Platform packages contain exactly one binary and set `os`/`cpu` in `package.json`.
- The umbrella package lists platform packages in `optionalDependencies`.
- Optional dependency versions must equal the umbrella package version from the same release.
- The umbrella `bin/bpi.js` shim resolves the platform package binary and spawns it.
- No package may define `scripts` or postinstall hooks.

The shim must fail with one actionable message for:

- `--no-optional` or `--ignore-optional` installs.
- pnpm isolated linker layouts.
- Yarn PnP virtual filesystem cases where resolving succeeds but spawning does not.
- Unsupported platform/architecture.
- Version skew between the umbrella and platform package.

### PyPI

Build wheels by hand from the manifest:

- One wheel per platform tag.
- Put the binary under `<dist>.data/scripts/bpi` so pip installs it into the user's bin path.
- Include correct `METADATA`, `WHEEL`, and `RECORD`.
- Validate `RECORD` hashes and sizes after archive creation.
- Support pipx by adding the metadata pipx expects for command discovery if needed.

Linux wheel tags are a release decision, not a label to guess:

- If using `manylinux_*`, build inside the matching manylinux image and prove the glibc baseline.
- If using musl static binaries, tag as `musllinux_1_2_*`.
- Do not publish a Linux wheel until the binary's libc expectations match the wheel tag.

### Homebrew

Generate a formula from the manifest:

- Use `on_macos` and `on_linux`.
- Use `Hardware::CPU.arm?` branches.
- Use the manifest URL and `sha256` for each target.
- Use direct binary download or `using: :nounzip` when the artifact is already a binary.
- Homebrew has no Windows path.

### Windows

Windows is deferred for the first release unless a concrete user requirement moves it up.

The schema and manifest should still reserve `platform: "win32"` so adding Windows does not reshape
the contract later. When Windows is promoted:

- npm gets `os: ["win32"]` platform packages.
- PyPI gets `win_amd64` and `win_arm64` wheels where supported.
- Scoop is the first Windows package-manager wrapper because it mirrors the Homebrew manifest model.
- WinGet is an asynchronous publishing track and must not block a release.

## Security And Trust

Manifest hashes verify artifact integrity only after the manifest is trusted. Runtime trust roots
still differ by ecosystem:

- npm users trust the npm registry package they install.
- Python users trust PyPI and the wheel metadata.
- Homebrew users trust the tap commit and downloaded artifact hash.

Optional hardening:

- Sign the manifest with sigstore.
- Produce SLSA provenance tying schema commit, generated source commit, build environment, binary
  hashes, and package-wrapper archives together.
- Bake the schema commit/version into the binary and expose it through `bpi version --json`.

## Guard Rails

Audit the final archives, not just staging directories.

Required assertions:

- The manifest validates with Zod.
- Every manifest artifact URL has exactly one final binary.
- Final binary `sha256` and size equal the manifest.
- npm umbrella optional dependency versions exactly match the same release's platform package
  versions.
- npm packages contain no `scripts` fields.
- npm platform packages contain exactly one binary and no source tree.
- npm package tarballs contain no workspace references, `file:` deps, monorepo paths, `.github`,
  `node_modules`, source maps, or private build paths.
- Wheels contain exactly one binary under `.data/scripts/`, correct `METADATA`, correct `WHEEL`,
  and correct `RECORD` hashes/sizes.
- Homebrew formula hashes exactly match the manifest.
- The binary reports the same version, schema version, and schema commit as the manifest.
- Generated docs/OpenAPI/CLI command inventory matches the schema-derived IR.

Keep forbidden package markers similar to existing release-script patterns:

```text
workspace:
file:
apps/web
packages/db
tools/pipeline-v2
.github
node_modules
```

The final forbidden list should be specific to the CLI package once `apps/cli` exists.

## Rollback

Plan rollback before publishing:

- A single `yank` command should accept one manifest reference.
- For npm: deprecate the umbrella and platform packages with an actionable message.
- For PyPI: yank the affected wheels.
- For Homebrew: revert the tap commit or push a corrected formula.
- For CDN/object storage: keep bad binaries available if package ecosystems reference them, but mark
  the manifest as yanked and prevent new installs through package-manager metadata.

Rollback should not require manually discovering all package names; they derive from the manifest.

## Initial Implementation Plan

### Phase 1: Contracts

- Add Effect Schema runtime contracts for the Studio API and CLI command vocabulary.
- Add schema linter for verbs, flags, locality, output contracts, and override bounds.
- Generate OpenAPI and docs inventory from the same runtime value.

### Phase 2: CLI Source

- Add `apps/cli` as a Bun-first TypeScript package.
- Generate the command tree and dispatcher into `apps/cli/src/generated/`.
- Keep hand-written code limited to adapters: HTTP client, local config, auth, filesystem writes, and
  process output.
- Add `bpi version --json` with binary version, schema version, schema commit, and build target.

### Phase 3: Binary Release

- Add build targets for darwin/linux arm64/x64.
- Decide Linux wheel strategy before publishing PyPI wheels.
- Add macOS signing/notarization before computing hashes.
- Produce `CliReleaseManifest` from final bytes.

### Phase 4: Wrappers

- Render npm umbrella/platform packages.
- Render Homebrew formula.
- Add PyPI wheels only after Linux tag compatibility is proven.
- Keep Windows deferred but contract-ready.

### Phase 5: Publish And Rollback

- Add final archive audits.
- Add dry-run publish.
- Add manifest-driven yank.
- Add provenance/signing hardening when the first public release is close.

## Open Decisions

| Decision | Default |
|---|---|
| Public CLI package name | `bpi` for binary, scoped package name TBD |
| Manifest package home | Start in `packages/domain`, split to `packages/core` or `packages/cli-contracts` when release scripts appear |
| Windows | Deferred, contract reserved |
| Linux wheels | Blocked until manylinux vs musllinux is proven in CI |
| macOS signing identity | Required before public Homebrew/PyPI distribution |
| Package managers for first public release | npm and Homebrew first; PyPI after Linux tag proof |

## Verification

Before any CLI release is considered shippable:

- schema lint passes
- generated output drift check passes
- `bun test apps/cli packages tools tests`
- `bun build --compile` target matrix succeeds
- binary self-report matches manifest
- final archive audits pass
- install smoke tests pass for npm, Homebrew, and any enabled PyPI wheels
- rollback dry run lists every package/archive/formula derived from the manifest
