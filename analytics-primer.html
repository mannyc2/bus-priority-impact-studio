Why you feel lost (and the fix)

You're not confused because the system is bad. You're confused because a few plain ideas got wrapped in many similar-sounding names. This page teaches the handful of real ideas first, then hands you a decoder ring for every overloaded word. Everything here is pulled from your actual code, not generic transit theory.

The whole analytics system does one thing: it turns messy public transit data into a ranked, auditable list of hypotheses that a careful reviewer can trust enough to inspect — and it is obsessive about being honest about what it doesn't know.

Every detector, no matter what it looks for, returns exactly the same three-part output. Learn this triple and 70% of the confusion dissolves:

candidates[]"Here is a possible issue." A claim about a route/segment, with severity, confidence, and a score. Never published as-is.
evidence[]"Here's what backs it — and what argues against it." Typed links: primary, context, counter-evidence, caveat, missing-data.
coverage[]"Here is every place I looked, even where I found nothing." So silence is provable, not a gap.
The honesty rule, in one line: a route with no finding must be able to say which kind of nothing it is — "checked, no issue" vs. "couldn't check, data missing" vs. "source is stale." That's what coverage[] guarantees, and it's the spine of the whole design.

Read sections ① and ② for the mental model. ③–⑥ define the four real nouns (feature, detector, finding, claim posture). ⑦–⑨ are reference. If you only read one thing while stuck, read ⑩ — the overloaded-words decoder. That section exists specifically for the feeling you described.

①The four layers

The codebase is split into four rings. The split exists to answer one question: "is this code allowed to touch the disk / network / the public?" Click each layer to expand.

The cardinal rule that explains the whole split: math lives in the kernel and never does I/O; I/O lives in the pipeline and never does math; the public only ever sees approved output. When you feel an abstraction is "pointless indirection," it's almost always enforcing one of these boundaries.

②End-to-end: from raw rows to a published claim

This is the single most useful thing to internalize. One detector run walks down this staircase. Click any step to see what actually happens and which function does it.

Notice the hard wall at step 10→11: only a PromotedFinding — an immutable, hashed record traceable to a human decision — is allowed past it. Raw candidates never reach the website. That wall is the reason for half the "extra" types you've been tripping over.

③Features & resolvers — typed, quality-tagged inputs

A feature is the clean, typed input a detector eats. Raw SQLite rows are untyped and messy; a FeatureResolver turns them into a typed object at a declared grain, every one carrying a quality stamp.

Grain = the unit of one row

A "grain" is what one feature row is one of. The contract also records which axes were kept and which were collapsed (averaged away) — so you always know what detail you can and can't claim.

Real grains in your registry:

customer_journey segment_daypart route_month route_segment_month stop_direction_hour route_reliability_month rider_weighted_excess_wait route_direction_daypart route_metric_history feed_health intervention_window intervention_panel positive_deviance context_source route_treatment_summary

The quality stamp

Every feature carries data-quality flags so detectors can skip honestly instead of guessing on thin data:

coverageStatus sufficient / insufficient
freshnessStatus fresh / stale
sampleStatus supported / insufficient
sampleCount the raw N
FeatureContract vs FeatureResolver vs Feature. The contract (in packages/analytics) is the spec — "this grain has these keys, these required fields, comes from these tables." The resolver (in packages/applied-research) is the function that actually reads SQLite and builds the typed object. The feature is the resulting object. Same noun, three roles: spec, builder, product.

④Detectors — pure functions that emit hypotheses

A detector is a pure, deterministic function: same features in → same {candidates, evidence, coverage} out. No database, no network, no clock, no LLM. That purity is why detectors are trivially testable and why they live in the kernel.

// the shape every detector satisfies (packages/analytics/src/core/detector.ts) type AnalyticsDetector<TInput> = { detectorId: DetectorId; // "persistent_speed_hotspot" version: string; spec: FindingDetectorSpec; // the review contract (see ⑥) featureGrains: readonly string[]; // which grains it eats scope: { kind: "route"|"segment"|"corridor"|"system"; ... }; run(input: TInput): { candidates, evidence, coverage }; };

The registry & the spec

A detector isn't just its function. The registry (ANALYTICS_DETECTOR_REGISTRY) binds it to metadata: its claim tier, baseline families, required data products, promotion gates, and retirement status. The spec (FindingDetectorSpec) is the human review contract: the exact question, the strongest allowed claim, required evidence, and known failure modes. A test asserts registry and specs never drift apart.

Thresholds, not magic

Each detector ships DEFAULT_*_THRESHOLDS (e.g. minHotspotScore: 60). These are the tuning knobs. Your house rule (from memory): keep them tight and calibrated to the real corpus — don't loosen a .max() cap just to fit model drift.

⑤Findings & the promotion lifecycle

"Candidate" and "finding" are not synonyms — that confusion bites everyone. A candidate is raw detector output. A promoted finding is what survives human review. Here's the exact ladder a candidate climbs (all types are real, in packages/domain/src/findings):

Each PromotedFinding is immutable and triple-hashed (decisionHash, candidateSnapshotHash, promotedFindingHash) — it freezes the exact candidate + the exact human decision + the approved evidence refs. That's how a published claim stays traceable months later.

Two label systems you'll see on candidates

severity — how much would it matter if true?
info · low · medium · high

confidence — how strong is the evidence it's true?
insufficient · low · medium · high

These are independent. High-severity + low-confidence is still worth a look. Don't conflate them.

claimSafeLabel — the reader-facing verdict that drives what the website is allowed to say:

no_issue_clean looked, all good
issue_clean real, well-supported
issue_needs_review borderline
insufficient_evidence can't say
source_lag_expected stale input

⑥Claim posture — how strong a thing you're allowed to say

This is the moral core of the system, and the source of three more confusable words. The promise: the system never says more than the evidence and the method allow. It's enforced by two ceilings — and the stricter one always wins.

Ceiling A — the claim-strength ladder (spec.allowedClaimStrength, 0–5)

Per-detector. The strongest wording a detector is ever allowed to produce, before review.

Ceiling B — the detector's claim tier (registry claimTier)

descriptive

States an observed fact. "This segment is slow." Needs coverage + sample gates.

associational

Relates a signal to peers / history / context / treatment. Needs cautious wording + reviewer approval.

candidate_causal_needs_review

Computes fields that could support "X caused Y." May only create a methodology-review candidate — never auto-publish causal language.

The rule: the public ceiling is the stricter of the spec strength and the registry tier, AND all promotion gates must pass, AND a human must approve. A high detector score cannot buy a stronger claim. This is why "did the bus lane cause the speedup?" is deliberately hard to ever say.

⑨Tier 1 vs Tier 2 — the biggest naming trap

There are two completely different pipelines that both use the words "feature," "candidate," and "promotion gate." Conflating them is probably 30% of your pain. Here's the clean split.

Tier 1 — Analytics detectors

Input is structured / real-time data (speeds, headways, ridership). Pure deterministic functions. Output is the {candidates, evidence, coverage} triple. No LLM anywhere. Everything in ①–⑧ above is Tier 1.

packages/analytics · packages/applied-research

Tier 2 — Document feature harness

Input is written documents. An LLM proposes extracted fields; deterministic validators prove or reject each one. A "feature" here = one extracted field with a proof state (verified / quarantined / …), nothing like a Tier-1 feature.

tools/pipeline-v2/.../docs/tier2/feature-harness

The Tier-2 harness pieces (compiler-style: propose → normalize → prove → gate)

Think of Tier 2 as a compiler with a type-checker: the LLM writes "source code," the validators are the type-checker, and the promotion gate refuses to "compile" (publish) if even one publishable field lacks proof (publishableFieldWithoutProofCount === 0). Verified Tier-2 fields then feed into Tier-1 detectors as evidence/context.

⑪Built vs aspirational (so you know what's load-bearing)

Part of "abstraction hell" is that some abstractions are real and wired, and some are scaffolding for a future that isn't connected yet. Knowing which is which tells you what you can safely ignore. Your own note: "weak analytics is an architecture problem, not a math problem."

✓ Built & wired

  • The detector kernel: 21 detectors, pure functions
  • Feature contracts + SQLite resolvers
  • Registry + specs with drift assertion
  • The candidate / evidence / coverage spine
  • Review packet → promotion queue → decision → promoted finding lifecycle
  • Detector readiness audit (ready/partial/blocked)
  • Calibration helpers (score vectors, gold-set eval shapes)
  • Tier-2 proof ledger + promotion gate (in progress)

○ Aspirational / not connected

  • causal/ — synthetic control, DiD, validity gates: typed, not wired into runs
  • forecasting/ — backtest/pinball scoring: types only
  • core/study — StudyDefinition/StudyRun harness: defined, not orchestrating
  • Persistent gold sets & false-positive register
  • Detector retirement / supersession logs
  • Fleet-complete feature materialization across all grains
  • Hard guarantee Studio reads only promoted findings
Practical takeaway: when you meet causal/, forecasting/, or StudyRun and can't see who calls them — that's expected. They're the planned ceiling, not the current floor. The live system is the detector spine in ①–⑥.
